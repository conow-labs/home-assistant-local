Conow Local 技术方案

Home Assistant 自定义集成 · Modbus RTU 本地接入 · 配置驱动实体模型

项目 local-ha / conow_local 版本 1.0.0 协议 Modbus RTU FC 0x03 / 0x06 HA ≥ 2026.6.0 更新 2026-07-07

设计目标

  • 通过 RS-485 本地读写 CONOW 阳台储能设备，无需云端账号
  • 遵循 Home Assistant 集成规范：config_flow + DataUpdateCoordinator + 多平台实体
  • 配置与代码分离：寄存器与实体定义集中在 registers.json，降低后续协议扩展成本
  • 控制写入后立即读回，保证 UI 与设备状态一致

1. 概述

Conow Local 是面向 CONOW 阳台光储一体机的 Home Assistant 自定义集成（domain: conow_local）。 它基于厂商 Modbus RTU 协议，在主机串口上与设备通信，将监控寄存器映射为 sensor / binary_sensor， 将控制寄存器映射为 number / switch / select。

与云端 Tuya 集成相比，本方案特点：

维度Conow Local云端集成
连接RS-485 / USB 串口互联网 API
延迟毫秒级轮询（默认 5s）依赖云与长连接
离线局域网内可独立运行需外网
扩展点位改 JSON + 翻译依赖 DP/云协议

3.2 核心设计模式

模式应用位置说明
Config Flow config_flow.py UI 向导采集设备名、串口、从站、波特率；probe_connection 读 SOC 验证连通性
Coordinator coordinator.py 单一数据源；async_add_executor_job 避免阻塞事件循环
配置驱动 registers.json 寄存器与 HA 实体解耦于 Python 硬编码
写后读回 _write_and_read 控制操作在同一把锁内：写 → 0.3s → read_all → 刷新实体

3.3 Config Entry 与多设备

每个物理连接对应一个 config entry，包含：

  • device_name — 用户在 UI 填写的展示名称（非写死）
  • modbus_port — 串口路径
  • modbus_slave — 从站地址（默认 160 / 0xA0）
  • modbus_baudrate — 波特率（默认 38400）

防重复键：unique_id = modbus_{port}_{slave}_{baudrate}。 设备注册标识：identifiers={(DOMAIN, entry_id)}，实体 unique_id = {entry_id}_{code}。

多从站同一串口：当前每个 config entry 独立打开串口客户端。 若两条 RS-485 从站共用一个 USB 口，多个 entry 可能争用串口。 推荐「一 USB 一设备」；多从站总线共享需后续引入全局 Bus Manager（见第 9 节）。

4. 数据流与通信

4.1 定时轮询（默认 5s）

Coordinator._async_update_data() │ └─► executor: client.read_all() │ ├─► FC 0x03 addr=10000 count=37 (monitoring) │ inter-frame delay 0.15s └─► FC 0x03 addr=10100 count=8 (control) │ └─► decode_block → coordinator.data monitoring: { name: { raw, value, unit, bits? } } control: { name: { raw, value, unit } }

MONITORING_COUNT / CONTROL_COUNT 由 registers.json 中各 block 最大地址自动计算，新增寄存器无需手改常量。

4.2 控制写入与读回

用户操作 number / switch / select │ └─► coordinator.async_write_*() │ └─► _write_and_read() [threading.Lock 独占串口] │ ├─► client.write_register / write_force_mode ├─► sleep(POST_WRITE_DELAY_S = 0.3s) └─► client.read_all(log_info=True) │ └─► async_set_updated_data() → 实体立即刷新

4.3 Modbus 参数

参数默认值说明
从站地址160 (0xA0)config entry 可覆盖
波特率38400 8N1协议出厂默认
读功能码FC 0x03读保持寄存器
写功能码FC 0x06写单寄存器
重试3 次失败重连串口、刷新输入缓冲
轮询间隔5sMODBUS_POLL_INTERVAL，协议要求 ≥2s

4.4 物理量解码

physical = (raw - offset) × scale
raw      = round(physical / scale + offset)
dtype占用寄存器典型用途
uint161SOC、电压、开关量
int161有功功率（正负表示方向）
uint322（连续）累计电量等大计数

5. registers.json 配置模型

registers.json 是运行时唯一配置源，由 register_map.py 在进程内缓存加载（lru_cache）。

5.1 顶层结构

字段类型说明
versionnumber配置 schema 版本
blocksobjectModbus 读块起始地址（monitoring / control）
sequencesobject多寄存器有序写入（如 force_mode）
registersarrayModbus 寄存器定义
entitiesarrayHome Assistant 实体定义

5.2 registers 条目

{
  "code": "battery_voltage",
  "address": 10002,
  "block": "monitoring",
  "dtype": "uint16",
  "scale": 0.01,
  "offset": 0,
  "unit": "V",
  "writable": false,
  "decode": "bitmask"
}
  • code — 逻辑名，全局唯一，作为解码字典 key
  • block — monitoring 或 control，决定归入哪次 FC 0x03 读块
  • decode: bitmask — 仅 system_status；解码时展开 bits 供 binary_sensor 使用

5.3 sequences.force_mode

强制充放电需按协议顺序写三个寄存器，非单点写入：

"sequences": {
  "force_mode": {
    "registers": [
      "target_charge_discharge_power",
      "charge_discharge_direction",
      "charge_discharge_cutoff_soc"
    ],
    "idle_register": "charge_discharge_direction",
    "idle_value": 0
  }
}

对应实体 write_handler: "force_mode"，由 select.py 触发 client.write_force_mode()。

6. 实体与设备模型

6.1 平台映射

platform数据源写入行为
sensormonitoring.register只读
binary_sensormonitoring.register + bit只读
numbercontrol.registerFC 0x06 物理量
switchcontrol.register写 0 / 1
selectcontrol.registeroptions 映射 raw；可挂 write_handler

6.2 实体命名与翻译

  • 代码侧：translation_key = entity.code
  • 文案侧：strings.json + translations/zh-Hans.json 中 entity.<platform>.<code>.name
  • select 选项文案：entity.select.<code>.state.<option_key>

strings.json 为 HA 默认回退文案，不可删除；英文可与 translations/en.json 合并维护。

6.3 设备展示

所有实体 _attr_has_entity_name = true，UI 显示为：

「{device_name}」 + 「{entity translated name}」
例：阳台储能 · 电池 SOC

7.3 扩展边界（需改代码）

场景改动点
新的多寄存器写序sequences + client.py + select.py 新 handler
FC 0x10 写多寄存器client.py 新增写方法
新 platform（如 button）新增平台模块 + PLATFORMS + entity_factory
JSON schema 校验可在 register_map.py 启动时增加校验器

7.4 版本与兼容

  • registers.json.version 预留 schema 演进
  • 实体 unique_id 基于 code，重命名 code 会导致 HA 产生新实体
  • 修改 scale 会影响历史统计语义，应视为破坏性变更

9. 限制与演进路线

9.1 当前限制

  • 单 entry 单串口单 coordinator；RS-485 多从站共享同一 USB 未统一调度
  • 仅 FC 0x03 读、FC 0x06 写；未实现 FC 0x10
  • registers.json 无 JSON Schema 运行时校验
  • macOS 开发环境 HA 偶发 exit 139，与本地 Core 构建相关，非集成逻辑必现

9.2 建议演进

优先级项收益
P1全局 SerialBusManager（按 port 复用，多 slave 轮询）一条 RS-485 多设备
P1registers.json JSON Schema + 集成重载校验配置错误早发现
P2从 CSV/XLSX 生成 registers.json 脚本协议文档与实现同步
P2force_mode 写入前校验 power / cutoff 非零避免无效强制充放
P3诊断实体暴露末次 Modbus 错误与 RTT现场排障
